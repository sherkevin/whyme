# PA 1.0 阶段一验收标准

## 一、PA 1.0 的整体分期视角

PA 1.0 采用分阶段递进式交付，每一阶段解决不同层级的问题，前一阶段的产出是后一阶段的前置条件。

- **阶段一**
  建立 PA 1.0 的基础系统结构，定义规则、数据模型和接口，打通最小信息流，确保后续阶段不会因结构问题返工。

- **阶段二**
  在阶段一结构之上，引入 Capture / Agent Tick 等机制，形成第一个"可运行闭环"。

- **阶段三**
  引入 Agent 核心能力、Skill、Demo 场景，使系统具备明确的 Agent 行为与可演示价值。

- **阶段四**
  引入 Search、Ingestion、Insight 等能力，完成 PA 1.0 的整体收口。

阶段一是所有后续阶段的工程与产品前提，其目标不是功能丰富度，而是结构稳定性。

---

## 二、阶段一在 PA 1.0 中的产品定义

阶段一是 PA 1.0 的基础阶段，其产品定义为：

**在不引入复杂 Agent 行为和自动执行能力的前提下，完成 PA 的基础系统结构、核心数据模型和接口定义，并确保最小信息流可以稳定运行。**

阶段一的产出应满足以下条件：

- 产品规则明确，不再频繁调整
- 数据模型和接口定义冻结
- 前后端可以独立推进开发
- 系统可以本地运行并部署

阶段一不要求系统表现出"智能效果"，只要求系统结构正确、边界清晰、可持续扩展。

---

## 三、阶段一必须完成的系统范围

阶段一只覆盖基础系统能力，不引入复杂业务逻辑。

系统范围包括：

- **用户与鉴权基础能力**
  系统能够区分不同用户，并保证数据隔离。

- **Inbox 模块**
  系统能够接收、存储和管理原始输入信息，作为后续处理的统一入口。

- **Today 视图所需的数据支持**
  系统能够提供一个稳定的数据结构，用于前端展示用户当前需要关注的信息。

- **基础工程与部署能力**
  系统可以在本地或新环境中启动，不依赖临时配置或手工操作。

该阶段不涉及任务自动推进、Agent 决策、Skill 执行或跨系统集成。

---

## 四、阶段一后端验收标准

阶段一后端验收以可运行性、结构稳定性和接口可用性为准。

后端必须满足以下条件：

### 项目工程基础

- ✅ 项目工程结构清晰，代码分层合理（如 API / Domain / Data / Agent）
- ✅ 项目可以通过标准方式启动（本地或 Docker）
- ✅ 数据库初始化流程完整（Schema、Migration、Seed）

### 鉴权与用户相关能力

- ✅ 实现 JWT 登录机制
- ✅ 提供获取当前用户信息的接口（如 `/me`）
- ✅ 用户配置（UserSettings）可读写
- ✅ 不同用户之间数据完全隔离

### Inbox 模块能力

- ✅ 定义 InboxItem 数据模型并冻结字段
- ✅ 支持创建原始 InboxItem（raw input）
- ✅ 支持 InboxItem 列表查询（分页、状态过滤）
- ✅ 支持 InboxItem 状态更新（如 raw / processed / archived）
- ❌ 不在 Inbox 模块中引入任何智能处理或自动转换逻辑

### Today 接口能力

- ✅ 提供 `/today` 接口
- ✅ 返回结构与接口定义文档一致
- ✅ 返回内容可以为 mock 数据或简单聚合数据
- ✅ 不因前端调用出现异常或不稳定行为

### 部署与交付能力

- ✅ 提供 Dockerfile 或 docker-compose
- ✅ 环境变量配置清晰
- ✅ 系统可在新机器或新环境中成功运行

---

## 五、阶段一前端验收标准

阶段一前端验收以工程可运行、页面结构清晰、状态完整为准。

### 前端工程基础能力

- ✅ Next.js 项目初始化完成
- ✅ 路由与 Layout 结构稳定
- ✅ API Client 封装完成
- ✅ 鉴权与路由守卫生效
- ✅ Loading / Error / Empty 状态完整

### Today 页面能力

- ✅ Today 页面路由存在并可访问
- ✅ 页面布局固定，不依赖未完成模块
- ✅ 能展示来自后端的数据结构（真实或 mock）

### Today 页面展示内容要求

- ✅ 显示 Inbox 中待处理项数量
- ✅ 展示 Today 列表（InboxItem 的投影）
- ✅ 支持基本的完成与排序交互
- ✅ 明确区分原始输入与今日关注内容
- ✅ 提供输出建议区域（仅 UI 结构，明确为 mock）
- ✅ 在无数据时提供明确的空态与新手引导

前端在阶段一不需要实现复杂交互或智能逻辑，但必须保证所有状态可正常渲染。

---

## 六、阶段一不纳入验收范围

以下内容**不**作为阶段一完成的判断条件：

- ❌ Agent 决策质量或智能水平
- ❌ 自动执行行为（下单、发送、调度等）
- ❌ Search / 向量检索
- ❌ Insight / Reflection / Skill
- ❌ 社交、通知、跨系统协作
- ❌ 复杂数据分析或推荐逻辑

如有实现，不计入阶段一价值，也不作为验收加分项。

---

## 七、阶段一完成的最终判断标准

阶段一视为完成，必须**同时满足**：

1. ✅ 产品规则、数据模型和接口已冻结
2. ✅ 前后端可以独立开发，不相互阻塞
3. ✅ Inbox → Today 的信息流稳定运行
4. ✅ 系统可在新环境中启动
5. ✅ 未引入超出阶段一范围的复杂功能

### 当前项目已实现的功能

根据 PRD4 的实际实施情况，当前项目已完成以下阶段：

#### ✅ Stage 1: 项目初始化和基础架构
- 项目结构搭建
- 数据库模型定义
- 基础配置

#### ✅ Stage 2: 核心数据模型
- Workspace, Area, Project, Item 模型
- TaskExtension, DecisionPoint, LedgerEvent 模型
- GraphEdge 模型（认知图谱）

#### ✅ Stage 3: 连接引擎（Connection Engine）
- 连接计算和存储
- 强连接过滤
- 连接统计

#### ✅ Stage 4: 微信集成
- 微信消息解析
- Web 爬虫
- 链接提取

#### ✅ Stage 5: 洞察挖掘（Insight Mining）
- LLM 抽象
- 洞察挖掘引擎
- Canonical Hash 去重

#### ✅ Stage 6: 可观测性与优化
- Request ID 追踪
- 性能监控
- 健康检查
- 日志系统

#### ✅ Stage 7: 安全与认证
- 用户认证模型
- JWT 令牌系统
- API 密钥管理
- RBAC 权限系统

### 与 PA 1.0 阶段一的对应关系

当前实现的 Stage 7（安全与认证）**基本满足** PA 1.0 阶段一的鉴权要求：

- ✅ JWT 登录机制（已实现）
- ✅ 用户信息接口（模型已实现，待实现路由）
- ✅ 用户配置可读写（UserSettings 模型已存在）
- ✅ 用户数据隔离（workspace_id 实现隔离）

**仍需补充的内容：**

1. **Inbox 模块**
   - 需要定义 InboxItem 模型
   - 实现 Inbox CRUD 接口
   - 实现状态更新接口

2. **Today 接口**
   - 需要实现 `/today` 端点
   - 返回 Today 视图数据

3. **API 路由实现**
   - 将已有的模型和工具函数封装为 FastAPI 路由
   - 实现完整的认证流程接口
