# PA 1.0 阶段二后端验收标准

## 一、PA 1.0 的整体分期视角

在 PA 1.0 的四个阶段中：

- **阶段一**
  完成系统骨架、规则冻结、数据模型冻结与最小信息流（Inbox → Today）。

- **阶段二**
  在阶段一结构之上，引入最小 Agent 行为与处理机制，使系统从"静态信息承接"进入"可被系统推进的状态"。

- **阶段三**
  扩展 Agent 能力与 Skill 体系，形成明确的 Demo 场景与复用能力。

- **阶段四**
  搜索、Ingestion、Insight 等能力收口，形成完整 PA 1.0。

阶段二是 PA 从"完善结构基础"走向"可运行闭环"的关键阶段。

---

## 二、阶段二在 PA 1.0 中的产品定义

阶段二是 PA 1.0 的最小可运行阶段，其产品定义为：

**在不追求复杂智能效果的前提下，引入最小 Agent 处理逻辑，使系统能够对 Inbox 中的信息进行一次受控处理，并将结果稳定反馈到 Today。**

阶段二关注的是：
- 系统是否能够自动推进一步
- Agent 行为是否可控、可解释、可回溯
- 信息是否从"被接住"变成"被系统处理过一次"

阶段二仍然不追求决策质量，而追求行为路径正确。

---

## 三、阶段二必须完成的系统范围

阶段二在阶段一基础上，新增且仅新增以下能力：

- **Capture / Agent Tick 机制**
  系统具备一个明确的处理入口，用于触发 Agent 对 InboxItem 的处理。

- **Inbox → Card / Today 的一次转换**
  原始输入可以被系统解析、整理，并生成结构化结果。

- **最小 Agent 行为**
  Agent 能够基于规则对信息进行一次处理，但不具备自主决策权。

- **状态推进与记录**
  系统能够记录：处理前状态、处理后结果以及处理时间点。

阶段二仍然不引入：
- 多轮复杂推理
- Skill 复用
- 自动执行
- Search / Insight

---

## 四、阶段二后端验收标准

阶段二后端验收以 **"系统是否能被 Agent 推进一步"** 为核心。

---

### 1. Capture / Agent Tick 机制

**必须实现**
- 明确的 Agent 触发入口（如 /capture、/agent/tick 或内部 job）
- Agent 只处理处于指定状态的 InboxItem
- 每次处理都有明确的输入与输出

**验收条件**
- 触发一次 Agent Tick 后，系统状态发生可预期变化
- 不会重复或越权处理同一 InboxItem

---

### 2. InboxItem 处理与状态推进

**必须实现**
- InboxItem 状态从 raw → processed
- 处理过程中生成结构化结果（如标题、摘要、类型）
- 原始输入与处理结果同时保留

**验收条件**
- 处理前后数据可对比
- 状态变化与结果生成可被查询

---

### 3. Card / Today 数据生成

**必须实现**
- 基于处理后的 InboxItem 生成 Card 或 Today Item
- Card / Today 数据结构与阶段一定义一致
- 不引入复杂业务分支

**验收条件**
- Today 接口返回的数据来自真实处理结果
- 不依赖纯 mock 数据

---

### 4. Agent 行为约束与记录

**必须实现**
- Agent 行为严格受规则约束
- 每次处理写入日志或事件记录
- 可追溯"哪个 InboxItem 被处理、产出什么结果"

**验收条件**
- 可以回看 Agent 对某条输入做了什么处理
- 不存在无法解释的状态变化

---

### 5. 稳定性与幂等性（基础级）

**必须实现**
- Agent Tick 具备基本幂等性
- 异常处理不会破坏整体状态
- 单条异常不影响其他 InboxItem

**验收条件**
- 重复触发 Agent 不导致重复生成结果
- 异常后系统可继续运行

---

## 五、阶段二前端验收标准

阶段二前端验收重点在于：**用户是否能感知到"系统已处理过信息"**。

---

### 1. Today 页面数据变化

**必须实现**
- Today 页面展示 Agent 处理后的结果
- 区分：
  - 原始输入
  - 已处理内容

**验收条件**
- 用户能看到 InboxItem 被系统"消化"后的形态
- 不再只是原始文本列表

---

### 2. Card 展示（最小版）

**必须实现**
- Card 基本结构（标题、摘要、类型等）
- Card 来源可追溯到原始 InboxItem

**验收条件**
- Card 与 InboxItem 存在明确关联
- 刷新页面后数据一致

---

### 3. 状态反馈与加载提示

**必须实现**
- 处理中的 Loading 状态
- 处理失败的 Error 状态
- 空数据状态不混乱

**验收条件**
- 用户不会因处理中状态误以为系统无响应

---

### 4. 非目标功能的明确隔离

**必须实现**
- 前端不暴露未实现能力入口
- 未完成模块保持不可操作状态

**验收条件**
- 用户无法触发阶段二不支持的操作

---

## 六、阶段二不纳入验收范围

以下内容**不**作为阶段二完成条件：

- ❌ Agent 决策准确率
- ❌ 多方案生成
- ❌ Skill 系统
- ❌ 自动执行或外部系统调用
- ❌ Search / 向量检索
- ❌ Insight / Reflection
- ❌ 社交与通知系统

---

## 七、阶段二完成的最终判断标准

阶段二视为完成，必须**同时满足**：

1. ✅ Agent 可以稳定处理 InboxItem 一次
2. ✅ Inbox → Card / Today 转换真实发生
3. ✅ 所有 Agent 行为可回溯、可解释
4. ✅ 系统在异常情况下不破坏整体状态
5. ✅ 未引入超出阶段二范围的能力
